# Releases

One directory per release, holding what is needed to redeploy or roll back that exact build.

```
releases/<tag>/
  image-digests.env         generated by infrastructure/gcp/deploy.sh at push time
  configuration-manifest.md the feature settings the release was validated under
```

**Digests, not tags.** `compose.gcp.yaml` pins every service by digest and marks each variable
required, so a deploy cannot silently fall back to `latest`. A tag is a mutable pointer — re-pushing
moves it, so a VM that reboots weeks later could pull different bytes than were tested, and "which
build produced this finding" becomes unanswerable (§19.2).

**Deploying a release**

```sh
set -a; . releases/<tag>/image-digests.env; set +a
docker compose -f compose.yaml -f compose.gcp.yaml up -d
```

On the VM this is automatic: `deploy.sh` puts the manifest in the compose bundle and `startup.sh`
appends its digests to the env file compose reads. A bundle without a manifest fails at boot with an
explicit message rather than starting on the wrong images.

**Rolling back** means sourcing an earlier manifest and bringing the stack up again. It restores
images and configuration only — it never modifies completed comparisons and never re-runs extraction.
